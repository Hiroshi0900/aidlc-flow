# aidlc-flow 縦切り開発サイクル設計

## 背景

[my-tasks #79](https://github.com/Hiroshi0900/my-tasks/issues/79) では、AI-DLCを使った開発に約23時間かかった一方、AI-DLCを使わない場合との比較基準がなく、継続可否を判断できないことが課題になっている。また、要件、実装、レビュー、結合テストが大きな工程として分離され、後工程の手戻りが複数Unitへ波及した。

次の比較作業では、機能を小さな縦切りにし、各切片をテスト、実装、レビュー、mainへのマージまで完結させる。これを繰り返すことで、途中成果を統合可能に保ち、所要時間と品質を比較できる状態を作る。

## 目的

`aidlc-flow` に再利用可能な `slice` ワークフローを追加する。1つのsliceを、ユーザーまたは外部利用者が認識できる小さな価値単位として扱い、1 intent、1ブランチ、1 PRでmainへ統合する。

成功条件は次のとおり。

- 要件からmainへのマージ準備までを、1つの短いサイクルとして実行できる。
- TDD、結合確認、独立レビュー、リポジトリ検査を省略せず、重複した承認やレビューを減らす。
- mainへ安全に入らない場合だけ、人へ分割方法や機能フラグの要否を確認する。
- 各sliceの時間、コスト、テスト、レビュー、未検証事項を比較可能な形で残す。
- Claude CodeとCodexの両方で同じ意味のワークフローを利用できる。

## 対象外

- AI-DLC本体へのアップストリーム貢献
- 自動デプロイ
- 人の承認なしでのpush、PR作成、mainへのマージ
- あらゆるsliceへの機能フラグの強制
- 大規模な事前設計文書やUnit別の重複文書
- AI-DLCを使わない比較実験そのもの。このワークフローは、比較対象となるAI-DLC側の測定可能な実行形を提供する。

## 採用する構成

`aidlc-flow` にプロジェクトローカルの再利用可能プラグイン `aidlc-flow-slice` を同梱する。公式AI-DLCの生成物を直接書き換えず、公式のプラグインとカスタムスコープの仕組みを利用する。

```text
aidlc-flow
├── plugins/aidlc-flow-slice/
│   ├── manifest
│   ├── slice scope
│   ├── slice-contract stage
│   ├── slice-review stage
│   └── merge-readiness stage
├── bin/aidlc-flow
└── tests/
```

初期対応バージョンはAI-DLC v2.9.0に固定する。プラグインのmanifestやステージ定義の正確なファイル形式は、v2.9.0のplugin buildと生成結果を契約テストで確定する。未確認の内部形式へ依存する実装は行わない。

## ワークフロー

1つのsliceは次の順序で進む。

```text
Initialization
    ↓
Slice Contract
    ↓
Code Generation（TDD）
    ↓
Build and Test
    ↓
Slice Review
    ↓
Merge Readiness
    ↓ push承認
push・PR作成
    ↓ CI成功・マージ承認
PR経由でmainへマージ
```

### Initialization

intentと作業ブランチを開始し、実行環境とリポジトリ状態を確認する。slice全体を単一の価値単位として扱い、水平なコンポーネント別Unitには分解しない。

### Slice Contract

実装前に、次の内容だけを固定する。

- ユーザーまたは外部利用者から観測できる受入条件を1〜3件
- 最初に失敗させる境界テスト
- 変更する外部境界と必要な結合確認
- 1 PRでmainへ安全に入るか

安全に入らない場合はここで停止し、sliceの分割、機能フラグ、一括実装のどれにするか人へ確認する。直近の既定は機能フラグなしとし、毎回の定型質問にはしない。

### Code Generation

受入条件をTDDで実装する。最初に失敗するテストを確認し、必要最小限の実装で成功させ、リファクタリングする。規模が大きい場合のみcodex-phase相当の小タスクへ分けるが、すべて同一sliceの受入条件へ収束させる。

計画承認はslice開始時の1回へ集約する。途中で契約を変える必要が生じた場合だけ再承認を求める。各小タスクはテスト成功と1意図のコミットまで完了させる。

### Build and Test

次の順で検証する。

1. 変更箇所に近い対象テスト
2. 変更した境界を通る結合テスト
3. リポジトリ標準の全体検査

外部サービスや実機との境界を変更した場合、適用可能な範囲でローカルまたは実環境の往復確認を最低1件実施する。失敗した場合はCode Generationへ戻り、レビューへ進まない。

### Slice Review

テスト成功後に、独立したレビューを1回行う。順序は以下とする。

1. Slice Contractの受入条件を満たすか
2. コード品質、エラー処理、セキュリティ、保守性に問題がないか

CriticalまたはImportantの指摘は必ず修正する。修正後は影響するテストとリポジトリ全体の検査を再実行し、変更された範囲を再レビューする。

速度を落とす重複レビューは行わない。公式Code Generation内のレビュー機構は無効化または最小化し、プラグイン所有の `Slice Review` を唯一の独立レビューとする。v2.9.0で安全に無効化できない場合は、Code Generation側を機械的な自己確認、`Slice Review`側を独立レビューとして役割分離し、同一観点の二重確認を禁止する。

### Merge Readiness

Merge Readinessは、まずローカルのマージ準備を検査し、人の承認後にpushとPR作成を行う。PR作成後はCI結果を同じステージで確認する。次をすべて満たした場合だけmainへマージ可能と判定する。

- 作業ツリーがクリーンで、意図した変更がすべてコミット済み
- mainの最新状態を取り込んだ後の検査が成功
- PRのCIが成功
- CriticalまたはImportantの未解決指摘がない
- 未検証事項と既知の制約が明記されている
- 人がmainへのマージを明示的に承認している

push、PR作成、mainへのマージは別々の外部操作であり、それぞれ実行前に明示的な承認を得る。PR作成後にCI失敗や競合が発生した場合は、同じsliceブランチで修正して検査とレビューを更新する。デプロイはこのワークフローに含めない。

マージ後はPR URL、マージコミットSHA、テストとレビューの証拠、所要時間、取得可能なコストを記録してintentを閉じる。次のsliceは更新済みmainから開始する。

## 失敗時の遷移

- **Slice Contractが大きすぎる、または安全に統合できない:** 実装前に停止し、分割方法を人へ確認する。
- **実装またはテストが失敗:** Code Generationへ戻る。
- **Slice Reviewで必須修正が発生:** 修正、Build and Test、影響範囲の再レビューを行う。
- **PR作成後にCI失敗または競合が発生:** 同じsliceブランチで修正し、検査と影響範囲のレビューを更新してマージ承認を取り直す。
- **未検証事項が残る:** Merge Readinessに列挙し、受入条件に関わる場合はブロック、それ以外は人の明示的な許容を求める。

未検証事項を暗黙に成功扱いしない。

## 成果物

文書は判断と証拠に必要な最小限へ絞る。

- `slice-contract.md`: 受入条件、境界テスト、統合可否
- `verification/slice-test-results.md`: 実行したテスト、結果、対象外
- `review/slice-review.md`: 指摘、対応、再レビュー結果
- `merge/merge-readiness.md`: コミット、CI、未検証事項、承認、マージ証拠

公式エンジンが提供する状態、再開、監査、取得可能なコスト記録は再実装しない。

## aidlc-flow initの動作

`aidlc-flow init` は次の順で処理する。

1. インストール済みAI-DLCが対応バージョンか確認する。
2. 既存の公式AI-DLC設定を行う。
3. 同梱した `aidlc-flow-slice` をインストールまたは更新する。
4. coreの `aidlc` と `aidlc-flow-slice` の両方を有効化する。
5. plugin buildでグラフとscopeを検証する。
6. 既存の共有Memoryをマーカー範囲内で更新する。
7. `aidlc doctor` で最終検査する。

Claude Codeでは `/aidlc-flow-slice <説明>`、Codexでは同等の `$aidlc-flow-slice <説明>` を入口とする。実際の生成コマンド名はv2.9.0のplugin projectionで確認し、両harnessの利用者向け表記をREADMEに記載する。

## 更新時の安全性

- workflow進行中はプラグイン更新を拒否する。
- 同じ入力で繰り返し実行しても結果が変わらない。
- 管理対象外の利用者ファイルを上書きしない。
- 管理対象プラグインが手編集されていた場合は上書きせず停止する。
- 非対応のAI-DLCバージョンでは理由を表示して停止する。
- coreの `aidlc` プラグインを無効化しない。
- 更新後のplugin buildとdoctorに失敗した場合は成功扱いにしない。
- 既存の未コミット変更を削除、stash、commitしない。

## テスト方針

プラグインとbootstrapについて、少なくとも次を自動検証する。

- slice scopeの経路に意図したステージだけが含まれる。
- Claude CodeとCodexの両projectionが生成できる。
- `aidlc-flow init` が冪等である。
- workflow進行中の更新を拒否する。
- 管理対象プラグインの手編集を検出し、上書きを拒否する。
- 非対応バージョンを明示的に拒否する。
- Build and Testの失敗がレビューへ進まない。
- レビュー指摘後に再検査と必要範囲の再レビューへ戻る。
- 未検証事項がMerge Readinessに残る。
- plugin build、`aidlc doctor`、リポジトリの `make check` が成功する。

実装はテストを先に追加し、失敗を確認してから最小実装を行う。

## 比較に残す測定値

AI-DLC継続判断のため、各sliceで次を記録する。

- 開始からマージ準備完了までの経過時間と実作業時間
- ステージ別の時間
- 人の承認・介入回数
- テスト失敗、レビュー差し戻し、再実行の回数
- 利用可能なモデル別トークン数とコスト
- 変更ファイル数、追加・削除行数、コミット数
- 発見した不具合と、どの段階で発見したか
- 未検証項目

AI-DLCなしのcodex-phase単体でも同じ項目を測り、規模が近い作業同士で比較する。単一の合計時間だけで優劣を判断せず、統合まで到達した品質証拠と手戻りも併記する。

## 導入判断

まずAI-DLC v2.9.0とaidlc-flowの範囲で実装し、実際のsliceを1件通す。その結果、レビューの一本化や必要なステージ遷移を公式プラグイン機構だけで表現できない場合は、非公開な内部ファイルの直接編集へ進まず、次のいずれかを改めて選ぶ。

1. 表現可能な範囲へワークフローを簡略化する。
2. aidlc-flow側のラッパーで不足部分を補う。
3. 公式AI-DLCへ機能提案または貢献する。

この順序により、保守負担を増やす前に効果を測定する。
